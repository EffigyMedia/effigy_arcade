### RLG-051 — A time-of-day setting in the pre-race menu
- **RULED 2026-08-28T17:50:07-04:00** — **Owner, 2026-08-28:** "Another setting I want added to the pre-race menu: time of day (dusk,
midnight, dawn, midday)."

**Most of this already exists, and that is the useful finding.** road.js:7380 runs a full day cycle
on a wall clock - `DAY_SECONDS = 240`, `dayClock`, and `phase()` returning 0 to 1 - with the four
points named in the code exactly as the owner named them:

| phase | the code's name | the owner's name |
|---|---|---|
| 0.00 | dusk | dusk |
| 0.25 | night | midnight |
| 0.50 | dawn | dawn |
| 0.75 | day | midday |

So this is not new rendering. `nightFall()`, `goldenBand()`, the sun and moon placement, the lit
signs, the verge dimming and the cruiser livery choice all already key off `phase()`. **The setting
is a starting value for `dayClock`, plus a control in the garage.** It should be a small unit, and
if it turns out not to be, that is a signal that something reads the phase in a way this note has
missed.

**It is a wall clock and not an odometer, deliberately** - the comment records that tying the cycle
to distance meant slowing down slowed time and flooring it sped time up, "a paradox you feel every
time you brake". Any implementation must not undo that.

**ONE THING IS UNDECIDED AND IT CHANGES THE BUILD. Put it to the owner.** Does choosing a time of day
set where the cycle STARTS, with the four minutes then running on as they do today - or does it PIN
the light, so "midnight" means the whole race is at night? The word "setting" fits either. They are
different features:

- **starting phase** is a one-line change at race start and keeps the cycle, which is what the
  engine was built around and what a 12-mile race currently shows off
- **pinned** means a race can be run entirely in the dark, which is a thing players ask for, but it
  makes `phase()` constant and nothing has ever run with it constant. The golden band, the sun
  placement and the headlight logic have only ever been exercised while moving

**Related but NOT the same thing:** [[RLG-044]] gives traffic muted palettes and racers saturated
ones. A pinned midnight would be the harshest test that colour still reads as a class signal when
there is very little light to read it by. Worth doing them in an order that lets the second check the
first.
- **RULED 2026-08-28T18:01:12-04:00** — **Owner's answer, 2026-08-28:** starting phase, and the cycle runs on. Shipped in v0.9.7.

A `TIMES` table of the four the cycle already names - DUSK 0.00, MIDNIGHT 0.25, DAWN 0.50, MIDDAY
0.75 - a `TIME` control in the garage that cycles them, `optTime` saved with the other options, and
one line in the run reset: `dayClock = TIMES[optTime].p * DAY_SECONDS`. No new lighting: every
renderer that cares already keys off `phase()`.

**It supersedes a deliberate decision, so the decision is quoted where it was made.** The reset
carried the line "dayClock deliberately NOT reset: the sky keeps its own time across runs" - a real
choice, not an oversight. The replacement says what overruled it and why: a setting the player
chooses that the game ignores because the previous run ended at 3am is not a setting. Continuity is
worth less than control. A later session finds the argument rather than an unexplained assignment.

**Verified by EFFECT, and the effect check is what caught the difference between a working feature
and a working button.** `drive-test` now makes two assertions: that TIME offers the four times and
wraps, and that the run actually STARTS there. MIDNIGHT is used rather than DUSK because DUSK is
phase 0 and 0 is also what an uninitialised clock reads - a test that passes when the feature does
nothing is not a test. Measured: phase 0.2517 against a set 0.25.

**The vacuity guard was run rather than assumed**, as this project requires. With the `dayClock`
assignment commented out, the label check STILL PASSED - DUSK, MIDNIGHT, DAWN, MIDDAY, wrapping
correctly - and the phase check failed at 0.014. So the label assertion alone would have shipped a
control that changed a word on a button and nothing else, which is a failure this project has had
before.

**`API.phase()` was added to the seam** and the reason is recorded there: it sits with `wet`,
`snowy`, `settle` and `biome` because it is the same kind of thing - what the world looks like now -
and a fork drawing its own sky needs it. It is also the only way to test this control at all.

**The saved value is range-checked rather than trusted**, so a save written by a future build with
more times in it cannot index past the end of this build's table.

**Process note.** The unit was opened AFTER the first edit, which the process forbids: the WIP
baseline for UNT-009 was taken over a dirty tree and is not a clean starting point. Nothing was lost
- the previous unit was committed before this work began, so the diff is still exactly this
feature - but the snapshot is not what it claims to be.

gates, `node --check` clean. That is a weaker claim than an attested run and the record says so.
