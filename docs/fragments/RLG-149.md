### RLG-149 — An older iPad cannot hold the frame rate, and the owner asks whether Godot with rasterized art is the answer
- **RULED 2026-09-01T17:17:46-04:00** — Owner, 2026-09-01, from two devices: "this game runs phenomenal on my iPhone 17 Pro Max but
when my daughter tried playing it on her much older iPad, it has like incredibly bad frame rate
issues. I'm wondering if it can be made much more performant if it gets translated to Godot
script and into Godot where we rasterize all the art."

THIS IS THE FIRST REPORT FROM A SECOND DEVICE AND THAT IS WHAT MAKES IT VALUABLE. Every frame
rate this project has ever measured came off one phone and a desktop browser, so a floor has
never been known. A device that cannot hold the frame rate is a measurement nobody had.

THE QUESTION HAS TWO HALVES AND THEY HAVE DIFFERENT ANSWERS.

    WOULD GODOT WITH RASTERIZED ART BE FASTER? Almost certainly yes, and that route is already
    the plan for each machine ([[RLG-002]]). Godot draws through the GPU; this draws through
    Canvas 2D, which on an older iPad is largely a CPU rasteriser. Turning the vector work
    into textures moves it from per-frame arithmetic to per-frame blitting.

    BUT IT IS NOT THE FIRST THING TO TRY, because the conversion is a rewrite and the cause
    has not been named. A rewrite that carries the same overdraw across gets a faster machine
    doing the same wasteful thing. And the codebase is meant to be the playable design
    document that the Godot build is made from - so the cheap wins are worth having whichever
    route is taken, since the tuning survives and the plumbing does not.

WHAT THE SUSPECTS ARE, IN THE ORDER THEY SHOULD BE MEASURED. All three are fill rate rather
than logic, which is what a device-dependent frame rate usually means: the same JavaScript runs
on both machines, and only the pixel throughput differs.

    OVERDRAW IN THE ROAD PASS, WHICH IS THE LARGEST BY FAR. `drawRoad` walks about 150 slices
    far to near, and each one fills the ground FULL WIDTH from its own line down to the bottom
    of the screen. That is deliberate - the note in the function explains that it is what
    builds the terrain silhouette over a brow - and it means the screen is painted something
    like a hundred times per frame before anything else is drawn. On a phone with the fill
    rate to spare that is free. On an older tablet it is the whole budget.

    GRADIENTS BUILT EVERY FRAME. `createLinearGradient` and `createRadialGradient` are called
    inside the draw, not cached: the bore builds one per wall and one per vault, the vignette
    and the damage wash build one each, and every lamp pool builds its own. A gradient object
    is not free to construct and none of them changes between frames of the same place.

    THE SCENERY IS ALREADY CACHED AND IS PROBABLY NOT THE FAULT. `sprite()` renders to an
    offscreen canvas and the plans are cached per place, so trees and buildings are blits
    already. That is worth knowing before anyone spends a day on them.

HOW TO ANSWER IT WITHOUT GUESSING. `tools/fps-test.py` already measures frames per biome and
already carries the warning that a single run is noise - it takes several samples and prints
the range. What it does NOT do is throttle, so it cannot stand in for the iPad. Two things are
needed: a CPU-throttled run so the desktop can act as the slow device, and a per-pass cost
breakdown so overdraw can be separated from everything else. Neither exists yet.

AND THE OWNER SHOULD BE ASKED WHICH iPAD IT IS. The answer changes what "much older" means by
a factor of several, and it decides whether this is a floor worth designing to or one device
below the line.

WHAT IS NOT IN SCOPE. [[RLG-002]] says not to invest in work whose only value is on the web. A
fill-rate fix is not that - it is the same overdraw in Godot - but a bundle-size or
cache-behaviour fight would be.
