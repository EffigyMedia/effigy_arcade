### RLG-155 — A repository name uses hyphens, and -dev marks a development repo
- **RULED 2026-09-05T10:30:41-04:00** — RULED by the owner, 2026-09-05, after they asked whether this repository was `effigy-arcade-dev`
and it was not: "there is a standard. Development, repose and production repos are separated. We are
supposed to use the standard GitHub nomenclature of - instead of _ and development repos -dev while
production repos drop the -dev."

THE STANDARD, AS IT APPLIES TO A REMOTE:
  - lowercase, and words joined by HYPHENS, never underscores;
  - a DEVELOPMENT repository carries a `-dev` suffix;
  - a PRODUCTION repository drops it.

THE PROJECT FOLDER IS NOT AFFECTED AND THE OWNER ASKED FOR THAT TO BE EXPLICIT. A project folder
keeps `Pascal_Snake_Case` with UNDERSCORES and NEVER takes a `-dev` suffix - `Effigy_Arcade`,
`All_In_Vane`, `Net_Lite`. `Project_Identity.md` section 5 owns that rule and it is unchanged. The
two namespaces are separate and already said to be: that same section states that a folder name "is
not the product name" and "does not change the remote". So a repository name is DERIVED from the
project name rather than equal to it - lowercase it, turn the underscores into hyphens, then add
`-dev` if it is a development repository.

THE ACCOUNT WAS THE EVIDENCE, not the memory of the rule. Fourteen repositories, and the standard
held in twelve of them:

    hyphen + `-dev`, private   code-continuum-dev, quietus-dev, grid-strikers-dev,
                               road-rage-2026-dev, deadweight-dev, orgoonizer-dev,
                               harmoniku-dev, tabelis-dev, net-lite-dev, eidetic-dev
    hyphen, no suffix, public  drinax-ref-console
    underscore, WRONG          effigy_arcade, tiny_arcade

The correlation between the suffix and visibility is exact: every `-dev` repository is private and
every repository without one is public. The two exceptions are both arcade projects, and the reason
is lineage - Effigy Arcade forked from Tiny Arcade and the name came across with it.

WHICH ANSWERS THE QUESTION THIS PROJECT ACTUALLY POSES. The owner noted that this repository is
"both a development and a production repo", because it is public and GitHub Pages serves `main`
directly, so a testable build is a release ([[RLG-066]]). Under the standard the discriminator is
VISIBILITY, and a public repository is the production one. So dropping `-dev` was already correct
and the only thing wrong was the underscore. The dev/production fusion is a property of the
workflow, not of the name.

RENAMED to `effigy-arcade` on 2026-09-05. The remote URL was corrected in the same minute rather
than left on GitHub's redirect, because `Development_Process.md` warns that the OLD NAME IS RELEASED
on a rename and can be claimed by anybody - a stale redirect would send commits into whatever
repository later holds that name. `gh repo view` and `git remote -v` were checked to agree
afterwards, which is that document's own procedure.

WHAT THE RENAME COST, measured rather than assumed. Nothing in the shipped product: the manifest
uses `start_url: "./index.html"` and `scope: "./"`, and every asset path is relative, so no shipped
file carries the repository name at all. Saves are untouched, because `localStorage` is scoped to
the ORIGIN `effigymedia.github.io`, which a repository rename does not change. What does break is
the installed web app on the owner's phone, which points at `/effigy_arcade/` and needs adding to
the home screen once more. The Pages URL is now `effigymedia.github.io/effigy-arcade/`.

THREE STALE REFERENCES WERE FIXED and one file was deleted. `CLAUDE.md`, a path comment in
`404.html` and the link in `docs/README.md` all named the old repository. `sync.sh` named it three
times and was deleted rather than corrected - it clones the remote into a temporary folder and
copies files over the top, which is from when this working folder was not a repository. The thread
has carried it as obsolete for some time and the rename is the occasion to finish it.

WHY THE DRIFT HAPPENED, which is the part worth keeping. The standard is NOT in the process corpus.
`Development_Process.md` says only that "the repository name matches the project name" - and the
project is `Effigy_Arcade`, so the underscore came from correctly following the written rule. The
written rule and the owner's standard disagree, and a session reads the written one. THE CORPUS EDIT
IS NOT DONE: the process documents live at the environment root and this project's own instructions
forbid editing them from project work, so it must be made from an Environment session. What that
edit has to say is the three bullets at the top of this fragment, plus a correction of the "matches
the project name" line to "is derived from the project name".

TINY ARCADE IS THE OTHER EXCEPTION AND WAS NOT TOUCHED. It is a separate repository, parked and
complete, and this project never reaches into it.

WHAT THE CORPUS NOW SAYS. `Development_Process.md`, in the Initialize step, no longer says "the
repository name matches the project name". It says the repository name is DERIVED from the project
name and is not the same string, with a four-row table - lowercase, hyphens never underscores,
`-dev` on a development repository, no suffix on a production one. It states that VISIBILITY is the
discriminator in practice, and it answers this project's own awkward case directly: where a project
ships from the repository it is developed in, that repository is the PRODUCTION one and takes no
suffix, because the suffix marks what a repository is FOR rather than who is working in it. The
`gh repo create` line above the rule also changed from `<Owner>/<Project>` to `<Owner>/<repo-name>`,
so the command stops implying the two are one string.

`Project_Identity.md` SECTION 5 WAS DELIBERATELY NOT TOUCHED. Project folders keep
`Pascal_Snake_Case` with underscores and never take a suffix. The owner asked for that to be
explicit and the new corpus text says it in the same breath as the repository rule.
