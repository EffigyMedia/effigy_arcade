### RLG-137 — An optimisation sweep - every bell and whistle at 60+ fps
- **RULED 2026-08-31T23:14:09-04:00** — OWNER, 2026-08-31: "One thing that I wanna do and it can be part of a future task Queue, is an
optimization sweep so we can have all the bells and whistles but at a 60+ FPS target."

TRACKED, NOT STARTED. What follows is measurement taken today rather than a plan, because the plan
should be written against numbers and the numbers are the part that is missing.

THE FIRST PROBLEM IS THAT THIS MACHINE CANNOT MEASURE IT, and that has to be solved before anything
is optimised. Nine samples per arm in a forest, on one unchanged build, span EIGHT FRAMES - 52.4 to
60.4. Every arm measured today overlapped every other arm:

    one rank,   1.5px far cutoff    52.4 - 60.4, median 57.2
    two ranks,  1.5px               44.0 - 60.4, median 55.6
    two ranks,  2.2px               49.2 - 60.4, median 54.4
    one rank,   2.2px               47.6 - 60.4, median 59.2
    five ranks, 2.2px               46.4 - 60.8, median 54.8

THE FOURTH ROW IS THE PROOF THAT THE INSTRUMENT IS THE PROBLEM. One rank with a tighter far cutoff
draws STRICTLY FEWER objects than the first row and scored a LOWER minimum. A configuration that
cannot be slower measured slower. Until that is fixed, an optimisation sweep cannot tell a win from
noise, and it will produce confident changes that do nothing.

SO THE FIRST UNIT OF THIS SWEEP IS THE INSTRUMENT, NOT THE ENGINE. Candidates, in the order they are
likely to matter: run the samples against a FIXED seed and a fixed stretch of road, because
`fps-test` currently gets a fresh road per load and the road decides the work; pin the biome AND the
hour AND the weather, since all three change the object count; take far more samples and report a
median with a confidence interval rather than a range; and run the browser with a fixed frame budget
rather than letting it choose.

WHERE THE WORK IS, from what is known rather than guessed:

    THE FOREST IS THE HEAVY CASE and always has been. Desert, mountain, tundra and swamp all sit at
    60. If the phone is slow anywhere it is here.

    THE SCENERY PASS IS THE LARGEST CONSUMER. A forest frame draws about 5,300 roadside objects in
    the forward view and, since 0.10.46, another 1,400 in the mirror. Each is a `drawImage` from a
    cache. That is the first place to look and the numbers above are the reason.

    THE MIRROR IS A SECOND FULL PROJECTION PASS, by design, and now carries a road, cars, a
    treeline, a horizon, precipitation, checkpoint boards, the finish banner and five ranks of
    scenery in 44 pixels.

    AND THERE ARE THREE LIVE LEVERS ALREADY - `API.mirrorRows`, `API.mirrorNear`, `API.mirrorMin` -
    so the mirror's cost can be traded off from a device without a rebuild.

WHAT MUST NOT HAPPEN, because this project has a ruling about it. The owner ruled on 2026-08-29 that
no car fades to a simplified render and the mirror setting went with it: "keep full, always use the
appropriate renders." An optimisation that draws WORSE things is not on the table. The answer is to
draw fewer things, or to draw the same things more cheaply.

AND THE TARGET IS A PHONE, NOT THIS MACHINE. Every number above is a headless desktop browser at
480x900. A sweep judged green here and never run on the device would be the same mistake as a green
harness standing in for a device report, which this project has made before.
