### RLG-002 — Mobile only: touch is the input, and the web build may be a prototype
- **RULED 2026-08-28T09:20:03-04:00** — - **Ruling, from the owner, 2026-08-25.** These four games target **mobile platforms only**. Touch is
  the input. **Keyboard, mouse and gamepad are out of scope** - not deprecated, not a lower priority,
  simply not part of what this product is.

- **What that settles.** Every input question from here answers itself: a control is designed for a
  thumb on a phone held in portrait, and a feature that only makes sense with a keyboard is not
  built. It also settles a class of past work. Tiny Arcade spent real effort making eighteen
  cabinets answerable from a keyboard and a gamepad, and that effort was correct for a product that
  ran in a desktop browser tab. It does not transfer.

- **What it makes redundant, stated plainly rather than acted on.** `Arcade.menu` in the shell exists
  to move a cursor through a cabinet's menus with arrow keys and a pad, and the pad-subscriber
  swallow in `pollPad` exists to serve it. The whole `A.pad` layer polls the Gamepad API. Every
  cabinet also binds its own keyboard handlers. **None of this is deleted by this ruling** - it is
  working code, it costs nothing at runtime beyond one poll, and removing it is its own unit of work
  with its own risk. The ruling records that it is no longer load-bearing, so a future session does
  not spend effort maintaining it or extending it to a fifth machine.

- **The consequence that is easy to miss: the drive harness steers with a keyboard.**
  `tools/drive-test.py` drives Highway and Raceway for thirty seconds by pressing keys. If keyboard
  input is ever removed from the two driving games, **that harness stops working, and it is the only
  automated proof that the driving engine still drives.** Removing desktop input therefore has a
  prerequisite: teach the harness to drive by touch first, then remove. In that order, and not the
  other one.

- **The web build may not be the shipping artifact.** The owner's stated route is either a binary
  wrapper around this HTML and JavaScript - the options are assessed in the frozen `SHIPPING.md` -
  or **a conversion to Godot**. That second route changes what this codebase is for: it becomes the
  playable design document that the Godot version is built from, rather than the thing that ships.
  **This is worth knowing before anyone invests in work whose only value is on the web** - a service
  worker tuned for offline, a PWA install flow, a bundle-size fight. None of that survives a Godot
  port. Gameplay, tuning, and the rules of each machine survive any route.

- **What is unchanged.** The PWA install path stays, because it is how the owner plays and tests the
  games on a phone today, and it costs nothing to keep. `pack.sh --standalone` stays, because it is
  the first half of the binary-wrapper route.
