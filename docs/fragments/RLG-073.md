### RLG-073 — Scenery pops in: street lamps are not clipped or culled like the cars
- **RULED 2026-08-29T10:20:14-04:00** — Owner, 2026-08-29, from the device: the street lamps pop in. They must be CLIPPED AND CULLED the same
way the cars are, and so must any scenery added later. Recorded rather than fixed, at the owner's
request.

The cars stopped popping in RLG-041, and what fixed them is a specific set of rules rather than a
general improvement: a whole-sprite cull that tests the sprite's own box rather than a fixed line
across the screen, a crest test that hides what a hill actually hides, and a fade over the last part
of the draw distance so nothing arrives at full opacity. Scenery went through none of that. It
appears when its segment enters the draw range, which is exactly the behaviour the cars had.

The lesson from RLG-041 that applies here is about the horizon test. Sprites were being rejected for
being above a line at 40 per cent of the canvas, which is not where the horizon is when the player is
on top of a hill looking down - so cars vanished while fully visible. Any scenery cull written from
scratch will reach for the same shortcut. It should use `drawSprite`'s rules rather than a second
implementation of them, which is also the point of the owner's phrasing: the same way as the cars,
not merely as well as the cars.

The work is therefore to route scenery through the same emit-and-cull path the vehicles use, and the
test is a run with the draw ledger on (`watchDraw`) showing scenery entering the frame the way a car
does - faded in over the last stretch of the draw distance, not switched on.
- **RULED 2026-08-29T15:15:56-04:00** — THE OWNER RESTATED THE SCOPE, 2026-08-29, and it is wider than the lamps:

  "As for the clipping/culling, we need all those slice drawn, scenery objects, including the light
   posts to use the same system that clips and culls vehicles relative the ground."

ONE SYSTEM, NOT A SECOND ONE THAT BEHAVES SIMILARLY. The cars stopped popping in RLG-041 through a
specific set of rules, and this fragment already records them. What the owner is asking is that the
lamps and every scenery object added by [[RLG-059]] go through THAT system rather than through a
parallel implementation of it, because a parallel implementation is a thing that drifts.

THIS NOW BLOCKS THE SCENERY WORK RATHER THAN FOLLOWING IT. [[RLG-059]] adds four or five kinds of
roadside object across five biomes. Written against the lamps as they stand, each one inherits the
pop and each one has to be fixed separately afterwards. Fixing the lamps first means the scenery is
written into a system that already works. The owner listed this last; the order is a judgement about
cost and it changes nothing about what is delivered.
- **RULED 2026-08-29T15:31:22-04:00** — THE LAMPS HAD NO OCCLUSION AT ALL, WHICH IS WORSE THAN HAVING A BAD ONE. The guard was
`!overBrow(z1, p1.y)`, and `overBrow` returns false on its first line - it was neutered when `crestY`
was re-enabled, and the note explaining that sits inside the function. The call site still reads as
though it is testing something, which is why nobody looked at it. A post behind a hill drew straight
through the hill; one coming over a brow arrived whole. That is the pop the owner reported from the
device.

ONE GATE, AND BOTH CALLERS USE IT. The owner asked for "the same system that clips and culls vehicles
relative the ground", and this fragment already said the work was to use `drawSprite`'s rules rather
than a second implementation of them. So the three cases are lifted out whole into `crestGate` -
entirely under the silhouette so cull, across it so clip to the band ABOVE the brow, otherwise draw -
and `drawSprite` and the lamp both call it. Nothing about the cars' behaviour changed: drive-test
came back 25/25 and the sprite counts are in their usual range.

THE FIRST VERSION OF THE CHECK WAS VACUOUS, AND ONLY FALSIFYING IT SHOWED THAT. The ledger counted
the outcome INSIDE `crestGate`, which records what the gate DECIDED. The defect being fixed is a
caller that asks and then ignores the answer, and such a caller produces an identical ledger. The
proof: the lamp's gate result was replaced with a constant "always draw", the harness was run, and
it PASSED at 441 clipped. The count moved to the branch that acts on the answer, the same defect was
put back, and it then failed at 0 clipped against 47 on the fixed build.

THE CULL COUNT IS NOT ASSERTED ON, DELIBERATELY. `hidden` came back 0 for the lamps on every run
here and 38 to 466 for the cars, and this harness already carries the reason: the terrain is
generated fresh per load and the cars' own cull swung 0, 40 and 147 on one unchanged build. An
assertion on it would fail at random and get the harness switched off, which is the failure mode
`occlusion-test.py` was written against. It is printed instead, with the reason next to it.

WHAT THE CLIP COUNT PROVES, and it is not a tuning result. Before this change a lamp could not be
clipped by anything, because nothing tested it. A non-zero count is a thing that could not happen at
all, rather than a number that got better.

NOT VERIFIED HERE. Whether the lamps still pop on the device is the owner's call. The mechanism
removed is geometric rather than timing-dependent, which is a reason to expect the fix to travel, and
that is the same reasoning that held for RLG-041 - where it took six fixes over eleven versions and
five of them were real mechanisms that were not the one being seen.
- **RULED 2026-08-30T23:19:24-04:00** — MEASURED, 2026-08-30, AND THE GEOMETRY IS NOT THE FAULT. Owner: scenery moves away far faster than it approaches - reported about the forward view, and visible in the mirror too.

PERSPECTIVE GIVES ONE LAW THAT CANNOT BE ARGUED WITH: apparent width times distance is a constant. Following one tree in from 30,000 units to 12,500 on a flattened road, that product holds at 275,141 with a drift of 0.00 per cent, and the frame-to-frame growth never exceeds 2 per cent. The size is exact and the position follows from the same scale. So nothing about where the scenery is drawn is wrong.

TWO MEASUREMENTS WERE WRONG BEFORE THAT ONE, AND BOTH WERE THE INSTRUMENT. The first waited 1.4 seconds of a 3 second count-in, so the car was stationary for most of the run and the object barely moved - the harness had caused its own number, which this project has now been caught by three times. The second read the road position AFTER the frame while the width was recorded DURING it: a frame of skew is up to ninety world units, which at the near end is a couple of per cent and reads exactly like the geometry drifting. The position is stamped with the width now.

AND THE ROAD HAD TO BE FLATTENED FIRST. On the shipped road an object near the horizon moves mostly because the terrain under it does; the first flat-road run still carried a 50-pixel jump, which was a hill and not a defect.

SO WHAT IS LEFT IS THE FADE AND THE DRAW DISTANCE, and both are taste rather than correctness. An object is invisible until about 30,000 units and does not reach full opacity until about 22,000 - which is the stretch where it is moving most slowly in screen terms. It therefore ARRIVES as a faint smudge that barely moves, and becomes solid just as it starts to accelerate past. That is a fair description of slow to approach and fast to leave, and it is produced entirely by when the object becomes visible rather than by where it is. The levers are the alpha ramp - full opacity at a quarter of the draw today - and DRAW itself. THE OWNER DECIDES, because there is no defect to point at.
